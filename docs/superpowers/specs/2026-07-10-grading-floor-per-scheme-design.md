# 整地方案樓板獨立化設計（樓板比照地形採「設計副本」模式）

> 背景對話：2026-07-10，使用者實際操作發現手動複製樓板調整範圍後，方案間樓板互相干擾可見。
> 本規格是 2026-07-02 `toposolid-footprint-cut-fill-design.md`「方案還原策略」節的修正案：
> 該節原假設「方案間僅樓板高程不同」是最常見情境、「輪廓不同」是邊角案例並拒絕自動處理；
> 本規格改為：樓板輪廓/範圍本來就會因方案而異是常態，樓板應與地形一樣各自獨立存在。

## 現況問題（為什麼要改）

1. **樓板現在是共用、會被覆寫的單一活元素**：`grade_toposolid_to_floors` 只複製地形（`RevitToposolidGradingAdapter.CreateDesignCopy`），樓板本身從不複製，只在登記簿記一份「當時的高度/輪廓快照」（`FloorMetric.HeightOffsetMeters`、`FloorGeometrySnapshot`，`GradingSchemeRecord.cs`）。
2. **`restore_grading_scheme` 因此只能處理「樓板高程不同」型方案**：把記錄的偏移數字寫回同一片活樓板（`CommandExecutor.GradingView.cs` 還原邏輯）；「樓板輪廓不同」型方案會被明確拒絕，引導使用者手動用 Design Option（2026-07-02 規格 183 行）。
3. **實測發現的操作痛點**：使用者做完方案一後，手動複製一份樓板調整範圍準備做方案二，這時方案一的樓板與方案二正在調整中的樓板同時存在、同時可見，互相干擾，且完全沒有任何工具支援去區分/隔離兩者——因為工具原本假設「樓板不會被複製」。

結論：樓板範圍/輪廓因方案而異是常態，不是邊角案例。樓板應該比照地形，走「每次整地建立一份設計副本」的模式。

## 核心決策：樓板也走「設計副本」模式

`grade_toposolid_to_floors` 執行時，除了現有的「複製地形設計副本」，**同時複製一份樓板設計副本**：

- 使用者選取的原始樓板（`floorIds` 指到的元素）永遠保持不動，角色比照「原地形」——是每次整地的取樣來源，不被工具修改或搬移。
- 工具實際整地/記錄所綁定的，是這次新複製出來的**樓板設計副本**，角色比照「設計地形」。
- 一個方案 = 一片設計地形 + N 片樓板設計副本（原本是 1 片地形 + 0 片樓板）。

這與現有地形機制完全對稱，可以直接沿用同一套已驗證過的手法，不是另起爐灶：

| 地形現有機制 | 樓板要新增的對應機制 |
|---|---|
| `CreateDesignCopy`（複製地形＋設定階段） | 新增樓板版 `CreateDesignCopy`（複製樓板＋設定階段，樓板不需要 Cut/Fill 所以不需要階段調整，但仍需要新建於目前階段，跟設計地形同批） |
| Comments 標籤「RevitMCP {方案名}」 | 樓板設計副本比照打上相同標籤，方便使用者在模型樹/明細表直接辨識 |
| `GradingSchemeRecord.DesignToposolidId` | 新增 `GradingSchemeRecord.DesignFloorIds`（每個原始樓板 ID 對應到它的設計副本 ID） |
| `CollectOtherTerrainIds` + `view.HideElements` | `CollectOtherSchemeFloorIds` 現有邏輯要改寫：現在收集的是「別的方案用到的**原始**樓板 ID」，要改成「別的方案的**樓板設計副本** ID」 |

## 視圖隔離：涵蓋正式輸出視圖，也要涵蓋草稿編輯階段

現有「方案視圖」(`create_grading_scheme_view`) 與共用的「整地檢視」(`show_grading_terrain`) 已經有一套視圖層級隱藏機制（`ApplySchemeVisibility`／`view.HideElements`，只對單一 View 生效、不影響其他視圖）。樓板設計副本納入後，這兩個視圖本來就會自動一併隔離樓板（因為隱藏清單改抓樓板設計副本 ID）。

但使用者提出的實際痛點是**做方案二之前、草稿編輯階段**——這時方案二可能還沒跑過 `grade_toposolid_to_floors`（還沒有正式的樓板設計副本），使用者只是在調整下一版樓板草稿，這時候仍想「不要看到方案一的樓板」。這個情境現有機制覆蓋不到，需要新增：

- 提供一個輕量操作（暫定併入「整地檢視」或另開一個共用的「樓板草稿」視圖，比照 `EnsureTerrainReviewView` 的「找不到就建立、找得到就重複使用」模式），讓使用者可以選「只顯示原始樓板／某方案的樓板設計副本」，把其他都藏起來，供編輯下一版草稿時使用。
- 這一項如果时间上排不進第一階段，退而求其次的做法是：至少把樓板設計副本打上清楚可辨識的 Comments 標籤，使用者可以自己在原生 Revit 用「暫時隱藏／隔離」或建一個 View Filter 手動處理——不理想但是零成本的過渡方案。

## 對「還原方案」的影響：這個功能的角色會被取代

一旦樓板也各自獨立，「還原方案」原本存在的理由（樓板只有一份、要用寫回高度數字的方式切換）就不成立了。切換到某個方案，會變成單純的「顯示這個方案自己的地形＋樓板設計副本，隱藏其他」——跟看地形是同一種操作，**不再需要對模型做任何寫入**。

建議：`restore_grading_scheme` 這個 MCP 工具＋「方案總覽」的「還原方案」按鈕，改造成純顯示切換（本質上變成 `show_grading_terrain` 的樓板版擴充，甚至可以直接合併成同一個操作：「回到方案 N」＝地形＋樓板一起切換顯示）。原本「僅樓板高程不同型」與「輪廓不同型」的分裂處理，這個改造後会自然消失——兩種情況都统一是「顯示切換」，不再需要區分。

舊有的 `rerunGrading` 參數（還原後選擇性重跑整地存新方案）需要重新設計語意，或者直接標記為此功能廢除後不再適用。

## 待決事項（需要使用者裁決，才能定案往下實作）

1. **面積/明細表重複計算風險**：樓板設計副本會被 Revit 的房間面積、明細表等一併算進去。假設一個模型有 3 個方案，同一片樓板會有 1 片原始＋3 片設計副本，共 4 片樓板同時存在——任何抓「全部樓板面積」的明細表都會被灌水 4 倍。要怎麼處理？
   - (a) 明細表加一個共用參數過濾條件（例如過濾「RevitMCP方案名＝空白」只看原始樓板），使用者自己在 Revit 原生明細表設定過濾器；
   - (b) 工具自動幫非目前方案的樓板副本打一個特殊參數/類別，供未來過濾邏輯用；
   - (c) 接受這個限制，於文件/工具提示明講「樓板明細表請自行加方案過濾」。
   這一項會影響要不要新增共用參數、新增什麼參數，需要先定案。
2. **是否每次都建副本**：地形是「每次執行都無條件新建一份設計副本」。樓板是否比照，還是只在「使用者確實想要不同輪廓」時才複製（例如加一個 `duplicateFloors` 參數，預設 true 或 false）？為了跟地形邏輯一致、避免「有時共用有時不共用」的心智負擔，傾向預設一律複製，但需要確認這不會造成使用者困擾（每次隨手測試都會多兩片樓板留在模型裡）。
3. **舊方案（本次改動前建立的）怎麼處理**：`GradingSchemeRecord.SchemaVersion` 需要升版（目前 5→6，新增 `DesignFloorIds`）。舊記錄沒有樓板設計副本，`restore_grading_scheme` 或未來的「切換顯示」邏輯遇到舊記錄時，行為要明確定義（例如：舊記錄繼續走現有的「寫回高度」邏輯，新記錄走「顯示切換」邏輯，兩套並存一段時間）。
4. **草稿編輯階段的隔離**：上面「視圖隔離」節提到的輕量操作，是否要排進這次實作範圍，還是先用「打標籤＋使用者自行用 Revit 原生隱藏」過渡，等實際用起來覺得不夠用再補。

## 實作影響範圍（初步盤點，實作前應再次核對行號）

- `MCP/Core/Grading/GradingSchemeRecord.cs`：新增 `DesignFloorIds` 欄位，`SchemaVersion` 升版。
- `MCP/Core/Grading/RevitToposolidGradingAdapter.cs`：新增樓板複製邏輯（比照地形 `CreateDesignCopy`）。
- `MCP/Core/Commands/CommandExecutor.ToposolidGrading.cs`：`GradeToposolidToFloors` 流程改為同時複製樓板，`BuildFloorMetrics`/`BuildFloorSnapshots` 改記錄設計副本而非原始樓板。
- `MCP/Core/Commands/CommandExecutor.GradingView.cs`：`CollectOtherSchemeFloorIds`、`ApplySchemeVisibility`、還原方案邏輯全部要改寫或大幅簡化。
- `MCP/Core/Commands/CommandExecutor.GradingViewer.cs`：`ShowGradingTerrain`（整地檢視）需要擴充成同時處理樓板可見性，或另外評估是否需要一個獨立的「樓板草稿檢視」。
- `MCP-Server/src/tools/grading-tools.ts`：`restore_grading_scheme` 的工具描述與參數需要依上面的「角色改變」重寫；`grade_toposolid_to_floors`、`solve_balanced_elevation` 的描述要補充「同時複製樓板」的行為說明。
- `MCP.Tests/Grading/GradingSchemeRecordTests.cs`：新增欄位的序列化測試。

## 近期可獨立實作項目：手動「樓板草稿複製」按鈕（2026-07-10 追加）

不用等上面「核心決策」的完整自動化機制到位，就可以先做這個——這是使用者主動準備下一版草稿的手動工具，跟「工具在整地當下自動複製樓板」是互補關係，不衝突，可以先後獨立上線。

**操作流程**：選取一片(或多片)樓板 → 按下新按鈕 → 工具複製選取的樓板、把原本那片在**目前視圖**隱藏(`view.HideElements`，只影響目前這一個視圖，不影響其他視圖，比照本規格與既有地形機制一致的做法)。

**用途**：做完一個方案後，要開始準備下一個方案的樓板草稿時，先按這顆按鈕拿到一份乾淨的複製版樓板來調整範圍/形狀，不會被前一個方案的樓板擋在視野裡，也不用自己手動複製＋隱藏兩個步驟。

**按鈕命名建議**：「複製\n樓板」。工具提示：「複製選取的樓板，並在目前視圖隱藏原本的樓板，方便你在複製出來的樓板上調整下一個方案的範圍。」

**與核心決策的差異**：這裡複製出來的樓板是使用者手動草稿階段的暫時產物，不需要地形設計副本那套 Comments/共用參數身分標記，也不會寫入登記簿——它只是在使用者按下「新整地方案」把它正式送進 `grade_toposolid_to_floors` 之前的暫存草稿。

**實作影響**：新增一個 Ribbon 按鈕＋Command 類別(比照 `GradingRibbonCommands.cs` 現有其他按鈕的寫法)；新增一個對應的 CommandExecutor 命令(建議命名 `duplicate_floor_draft`)做「複製選取樓板＋目前視圖隱藏原本」。

## 尚未涵蓋、留待後續的項目

- 樓板設計副本的「還原成新方案」語意（`rerunGrading` 參數的下一步設計）。
- 「方案總覽」視窗要不要同步顯示每個方案的樓板副本狀態（比照上一輪討論的方案視圖狀態欄）。
- 這份規格聚焦樓板本身如何獨立存在；出圖流程（各別出圖／比較出圖）若因樓板設計副本而需要調整（例如剖面裁切範圍改抓樓板設計副本而非原始樓板），需要另外核對 `CommandExecutor.GradingComparison.cs`／`CommandExecutor.GradingPresentation.cs` 是否受影響。
