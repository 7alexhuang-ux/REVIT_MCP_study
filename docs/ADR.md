# 架構決策紀錄（Architecture Decision Records）

本檔記錄 Revit MCP 專案「**為什麼這樣做**」。程式碼記錄「做了什麼」，[CHANGELOG.md](../CHANGELOG.md) 記錄「什麼時候做的」，本檔記錄「當初為什麼選這條路、放棄了什麼」。

格式：**背景 → 決策 → 理由 → 後果**。編號 `D-NNN` 只增不減；決策被推翻時**不刪除原條目**，改標記為「已被 D-XXX 取代」並保留原文——被推翻的理由本身就是資訊。

> 本檔建立於 2026-09-21。D-001 ~ D-004 為**回溯補記**：決策本身早已生效（多數寫在 `CLAUDE.md` 的禁止條款或 domain SOP 裡），但當時沒有記錄理由，此處依既有程式碼與文件反推補齊，並標注「回溯」。D-005 起為當下決策。

## D-001 單一 csproj ＋ 單一 addin manifest 支援 Revit 2022–2026（回溯）

**背景**：Revit 每個年度版本 API 不同（2022–2024 用 .NET Framework 4.8，2025–2026 用 .NET 8），常見做法是每版一個 `.csproj` 與 `.addin`。早期本專案曾出現版本別的專案檔（`RevitMCP.<年份>.csproj` 形式）。

**決策**：全專案只保留 `MCP/RevitMCP.csproj` 與 `MCP/RevitMCP.addin`，以 build configuration（`Release.R22` ~ `Release.R26`）區分版本，addin 組件路徑維持相對路徑 `RevitMCP\RevitMCP.dll`。

**理由**：
- 版本別檔案會各自漂移，改一處忘記另一處，實際踩過。
- Nice3point Revit SDK 已能用 configuration 切換 API 參照。
- 相對路徑讓 `install-addon.ps1` 能部署到任意使用者的 Revit 目錄，不必改檔。

**後果**：
- `CLAUDE.md` 列為**禁止條款**，QA/QC Phase 1-1 會掃出違規的版本別檔案。
- 代價：build configuration 增加時要同步 5 處；`verify-qaqc.ps1` 有對應檢查。

## D-002 Revit 端 WebSocket 一次只接受一個 MCP 連線（回溯）

**背景**：`MCP/Core/SocketService.cs` 以 `HttpListener` 在 `localhost:8964` 提供 WebSocket。多個 AI 客戶端（Claude Desktop、Claude Code、VS Code Copilot）都可能同時想連。

**決策**：同時只保留一條 MCP 連線；新連線會**取代**舊連線。多客戶端靠「切換」使用，不並行。

**理由**：
- Revit API 必須在 UI 執行緒執行，經 `ExternalEventManager` 排隊。多連線並行送交易會讓排隊語意與錯誤歸屬變得無法推理。
- 單連線讓「連線行為異常時重啟 MCP 服務」成為唯一且可靠的復原路徑。

**後果**：
- 文件（`CLAUDE.md`）明文禁止建議使用者同時跑兩個 MCP 客戶端對同一個 Revit session。
- 代價：無法做「A 客戶端查詢、B 客戶端寫入」的分工。目前沒有這個需求。

## D-003 domain（方法正本）與 skill（流程編排）分層（回溯）

**背景**：BIM 的法規檢討、量計算、審查方法，與「AI 該依什麼順序呼叫哪些工具」是兩種不同的知識。早期兩者混在一起寫。

**決策**：
- `domain/*.md` = 方法正本（公式、排除條件、扣除規則、邊界案例），**人與 AI 共讀**，維持中文可讀。
- `.claude/skills/*/SKILL.md` = 工作流程編排（工具呼叫順序），偏好英文。
- **衝突時 domain 勝**（`CLAUDE.md` 明文）。

**理由**：
- 方法會被引用到 PR、簡報、對外教學，必須是人看得懂的中文；流程編排只有 AI 在讀。
- 方法的壽命遠長於工具介面。工具改名時 skill 要改，domain 不該動。
- 讓「AI 用自己的常識算」這個失效模式有明確的擋點：`CLAUDE.md` 的 Domain Method Compliance 規則要求先讀 domain 再算。

**後果**：
- 新增 domain 需附 frontmatter（`domain/frontmatter-standard.md`），QA/QC 會檢查。
- 計數宣告（domain 數／skill 數）散落在 4 份正本文件，異動時要同步——已有 QA/QC 檢查把關。

## D-004 走動展示的影格由 Revit 逐格匯出，不交給 AI 生成影片（回溯）

**背景**：要做「業主簡報用的走動展示」，最直覺的做法是丟幾張圖給影片生成 AI，讓它生一段漫遊影片。

**決策**：影格**必須**由 Revit 沿相機路徑逐格匯出 PNG，每一格都記錄當時的相機位姿。

**理由**：
- 四視窗連動的骨幹是「相機路徑上的位置 t」：拖平面圖 = 換格，換格 = 移動 3D 相機。**AI 生成的影片沒有相機資料，無法與平面圖對位**，四窗連動就不成立。
- Revit 算出來的畫面是真實材質與陰影，幾何百分之百正確；生成式影片不保證門窗位置。

**後果**：
- 匯出期間 Revit 會暫時無回應（每格數秒），200 格可能超過 10 分鐘——這是已知且接受的代價，SOP 有明寫。
- AI 風格化被推遲成**後處理**（見 D-008），而不是生成方式。

## D-005 glTF 匯出以「空間裁切」取代「類別裁切」

**背景**：2026-09-21 實機跑 Snowdon Towers。`export_model_gltf` 預設沿用第一站視圖的可見性，撞上 200 萬三角面上限**提前停止**，產出 2,000,905 面／63.6 MB 的**不完整** glb（截斷點由幾何收集順序決定，可能砍掉相機正前方的牆）。

第一次的處置是改用只含樓板與牆的協調視圖當來源，面數降到 189,385、零警告——但使用者打開網頁後回報「根本看不出正常的室內外空間」：沒有門窗就看不到開口，沒有家具就分不出室內外，3D 視窗失去它唯一的用途。

使用者對「請你自己去 Revit 拉剖面框」的回應是：「**我怎麼知道會看到哪些內容？…你不是應該要找好一個最佳的方法嗎？**」

**決策**：`export_model_gltf` 預設 `bounds="path"`，從交付包 manifest 的相機路徑取樣點自動計算剖面框（水平外擴 `marginMeters` 預設 25 m、垂直 `belowMeters` 2.5 m／`aboveMeters` 8 m），套用到匯出用的暫存視圖。**保留全部類別**，只裁掉走動到不了的空間。`bounds="none"` 保留舊行為作為逃生口。

**理由**：
- 相機路徑就在 manifest 裡，「會看到哪個範圍」是**程式算得出來的**，不該要求使用者手動估算。
- 三角面預算是**空間問題**（整棟大樓 vs 一條走廊），不是類別問題。用類別裁切解空間問題，砍掉的正好是走動展示最需要的東西。
- 倉庫內已有同型做法可援引：整地工作流的 `ApplyFocusSectionBox`（`CommandExecutor.GradingView.cs`）就是「從分析範圍算剖面框並套到 3D 視圖」。
- 已查證業界主流的 Draco / meshopt 壓縮解的是**檔案大小**，解不了「匯出被截斷」；壓縮是可疊加的第二層，不是替代方案。

**後果**：
- 剖面框會在邊界切開牆體，從外部看模型會是切片狀。走動展示的 3D 視窗用途是定位與講解，可接受。
- 挑空、大廳等垂直向度大的空間需調大 `aboveMeters`，SOP 已註明。
- 三角面上限的警告文字改為指向調整裁切範圍，不再引導使用者去關類別。

## D-006 站點裁剪框必須沿用 Revit 既有的相機框 Transform

**背景**：`create_camera_stations` 建立的四個站點，匯出的 73 張影格**全部是空白**（每張僅 4.7 KB，畫面只有一條地平線），但同位置的 3D 視窗明明有幾何。同時 `get_camera_stations` 對四站都回報「裁剪區域未置中於視線」。

該警告曾被判定為誤報，理由是「讀回的 FOV 與請求值完全相同」。**這個推論是錯的**：FOV 由近角推算，近角正確不代表整個視錐正確。

**決策**：寫入站點裁剪框時，取 `view.CropBox`（`SetOrientation` 之後其 `Transform` 即為相機框）**就地替換 Min/Max 再寫回**，不再建立 `Transform.Identity` 的新 `BoundingBoxXYZ`。

**理由**：
- `CameraPathMath.CropBoxFromFieldOfView` 回傳的 Min/Max 定義在**相機座標系**（X 右、Y 上、Z 朝觀者、眼點在原點）。
- 讀取端 `ComputeViewFov` 正是用 `crop.Transform.Inverse.OfPoint(eye)` 反推眼點，**預期 Transform 是相機框**。
- 寫入端給 identity，等於把相機座標系的數值當成世界座標交給 Revit——寫入與讀取兩邊對同一個欄位的座標系約定不一致。

**後果**：
- 這是**唯一**的寫入點，修正後 `create_camera_stations` 建的站不再需要事後校準。
- 教訓已納入判斷原則：**用單一指標推翻一則警告之前，先確認那個指標涵蓋警告在講的東西**。
- 既有交付包的影格需重新匯出（相機框變了）。

## D-007 走動展示的核心差異是「與 Revit 雙向連動」，不是畫面品質

**背景**：2026-09-21 比對外部做法（archaiflow 的 Revit FBX 走查流程）：Revit 匯出 FBX → ChatGPT + Higgsfield 外掛產生純色分類 HTML → 匯出 PNG 序列 → Higgsfield/Genjutsu 出片。

**決策**：本專案走動展示的定位是**與 Revit 保持連線的雙向工作流**，而非「產生最漂亮的影片」。資源優先投入連動與回寫，不投入與生成式影片工具比畫質。

**理由**：
- 對方的流程在 FBX 匯出的瞬間就與 Revit **斷開**。改路線、改相機、改模型都要回 Revit 重匯、整條重跑。
- 我們是 MCP 連線且雙向：`get_camera_stations` 讀、`create_camera_stations` 建、`apply_camera_stations` 把網頁上拖過的站點**寫回 Revit 視圖**。模型改了重跑影格即可，不需重匯任何中介檔。
- 畫面品質可以靠外接工具補（D-008），但「斷線」是架構性的，補不回來。
- 附帶優勢：平面／剖面像素對位的四窗連動，需要相機資料才能成立（見 D-004），對方的流程結構上做不到。

**後果**：
- 對外說明與 `docs/PROJECT_INTRO.md` 應以「不斷線」為主訴求。
- 接受我們的預設畫面不如專業生成式影片；那一段外包給 D-008。

## D-008 AI 風格化外接 video-to-video；深度圖只對接受控制圖的工具有效

**背景**：`domain/walkthrough-package.md` §7 的「AI 風格化」一直標記為未實作。已實作的 `export_walkthrough_depth` 產出逐格深度圖，原本假設它能通用地幫助所有影片生成工具鎖住鏡頭運動。

2026-09-21 查證官方資料後發現這個假設不成立：

- **Higgsfield / Genjutsu**（[官方頁](https://higgsfield.ai/genjutsu)）只接受**來源影片 ＋ 參考圖 ＋ 文字**，未提及深度圖、分割圖或任何 ControlNet 類控制輸入。參考影片限 3–30 秒、最多 40 張參考圖。
- Higgsfield 另有 **MCP 介面**（`https://mcp.higgsfield.ai/mcp`），可由 Claude 直接呼叫，單段輸出上限 15 秒。
- 深度圖要配的是 Wan2.2 + VACE 那類**明確接受控制圖**的本機工具。

**決策**：
1. AI 風格化維持**外接**，不自建影片模型。
2. 深度圖定位為「**對接受控制圖的工具**的前置產物」，SOP 需明確標注它對哪類工具無效，不可宣稱通用。
3. 優先驗證路徑：先用 Higgsfield（有 MCP、最快接通）跑通一次端到端，再評估是否把 Wan2.2 架在本機 GPU。

**理由**：
- 我們的核心價值在與 Revit 的連動（D-007），影片模型是快速演進的外部商品，自建沒有優勢。
- 我們的來源影格是 Revit 算出的真實畫面（有材質、有陰影），**可直接作為 video-to-video 的來源影片**——對方之所以需要純色分類圖，是因為它的來源只有幾何沒有材質。**我們可能不需要分類圖**（未實測，也可能純色更乾淨反而更可控）。

**後果**：
- 「顏色分類圖」功能**暫緩**，等端到端實測結果再決定，避免做出可能不需要的東西。
- 成本進入評估範圍（不在既有訂閱內）：Higgsfield Starter $19/月起；對照組 Wan2.2 + VACE 本機零成本且吃深度圖。價格為 2026-09 第三方整理，**官方頁未能直接讀取，採用前須自行核對**。
- 15 秒／30 秒的長度上限會反過來約束交付包的單段站數設計。
