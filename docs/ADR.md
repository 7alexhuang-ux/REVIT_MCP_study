# 架構決策紀錄（ADR）

格式：背景 → 決策 → 理由 → 後果。編號 D-NNN 遞增，不刪不改舊條，要推翻就加新條並標「取代 D-xxx」。

---

## D-001 萬用窗：拓樸在生成時決定，尺寸在 Type 層活動，Instance 只留安裝參數
- 日期：2026-09-14
- 背景：萬用窗要能組態「幾排 × 幾樘、每格幾扇、每扇怎麼開」。社群調查顯示 Revit 2024 陣列數不能為 1、巢狀族切型別會破壞上層約束、All-in-One 超級族作者自承參數爆炸後改模組化；使用者擔心「活拉」造成門窗表失控。
- 決策：排數／樘數／扇數／開啟方式在生成時定死（一拓樸一族）；總寬總高、排高比、樘寬比、框料尺寸為 **Type** 參數（一尺寸一型別＝門窗表型號）；窗台高、框位置偏移、內外切透、開啟角度為 **Instance** 參數。
- 理由：門窗表以型別統計，與台灣門窗表「型號＋數量」邏輯一致；Instance 尺寸會讓每扇獨一無二、廠商無法報價；拓樸活調正是踩坑集中處。
- 後果：換組合＝換型別或用 MCP 重生，不在族內切換；專案內族數量隨拓樸種類增加（Phase 2 以 Type Catalog 緩解）。

## D-002 幾何由程式直接畫，不用巢狀零件族
- 日期：2026-09-14
- 背景：原提案為使用者手做固定／外推／橫拉／上懸四個扇族、程式組合。調查指出巢狀族需設共用才能上明細表、切型別破壞約束、巢狀越深檔案越肥。
- 決策：生成器在族內直接建擠出（框、扇、玻璃）、空心（MO）與符號線；扇數以參數上明細表。
- 理由：避開三個已知坑；拓樸既已定死，巢狀的可切換性沒有價值。
- 後果：框料是矩形示意實體，不是真實鋁材斷面；細緻級的斷面表現以線條與尺寸補足。

## D-003 Phase 1 固定尺寸，Phase 2 再做 Type 層活拉
- 日期：2026-09-14
- 背景：把幾何全數對齊鎖定到參考平面、標註綁參數、內部格線寫公式，Revit API 做起來脆弱，預估多 2–3 週且有做不到的風險。
- 決策：Phase 1 每個規格生一個尺寸定死的族（寬高進型別名），改尺寸用 MCP 重生；Phase 2 把外框與格線鎖到參考平面，讓同族複製型別改寬高。
- 理由：兩階段門窗表邏輯相同、同事操作不變；先證明管線再投資約束系統。
- 後果：Phase 1 族內 Width／Height 型別參數值正確但改了幾何不跟動，需在族說明與工具回傳的 warnings 明講。

## D-004 圖面慣例：三級對應比例、外推 30° 實線、三角形頂點頂到鉸鏈實際位置
- 日期：2026-09-14
- 背景：使用者回報粗略級線段散掉、外推扇平面被畫成門的 90° 全開；各國開啟符號慣例不同。
- 決策：粗略＝1:100 三線窗符號不畫開啟；中等＝1:50 框料矩形加外推 30° **實線**示意；細緻＝1:20 加軌道與交疊尺寸。立面外推三角形頂點在鉸鏈側且頂到扇框外緣，底邊在把手側扇框外緣兩角。
- 理由：使用者（事務所標準）拍板。
- 後果：符號用 symbolic curve 依詳細程度設可見性，不用可見性參數；其他事務所要改慣例走 `symbols` 旗標。

## D-005 橫拉交疊量預設等於扇框寬
- 日期：2026-09-14
- 背景：各鋁窗廠型錄不公開交疊量，調查只能標未查證。
- 決策：預設交疊＝扇框寬（兩支勾企完全重疊），可切手動值。
- 理由：使用者拍板的事務所慣例。
- 後果：扇框寬改動時交疊自動跟隨；規格 JSON 帶 `meetingRailOverlapMode`。

## D-006 MO 以空心擠出定義，可對內對外切透飾板；專案端切割由 MCP 套用
- 日期：2026-09-14
- 背景：外飾板／內飾板常是獨立元素，樣板的開口只切主體牆。
- 決策：族內空心＝框外緣每側加 MO 預留，深度自外飾板外再外切、自內飾板內再內切；族啟用「載入時以空心切割」；放窗後由 MCP 找出與空心相交的飾板元素逐個套用切割。
- 理由：Revit 不會自動切非主體元素，手動切割幾何是 BIM 常見漏做點，正好交給工具。
- 後果：飾板類別必須是可被空心切割的類別；切割 API 行為需在 2024 實測。
